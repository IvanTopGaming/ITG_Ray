# Диагностика IPv6 на Windows 10/11

Скрипт [diagnose-windows-network.ps1](../scripts/diagnose-windows-network.ps1) собирает состояние сети и проверяет HTTPS отдельно через IPv4, IPv6 и локальный SOCKS. Нужен Windows PowerShell 5.1 или новее. PowerShell 7 устанавливать не требуется. Если `curl.exe` отсутствует, сетевые HTTPS-пробы будут пропущены, остальные данные сохранятся.

Скрипт не меняет маршруты, DNS, реестр, брандмауэр, настройки VPN или служб. Он отправляет диагностические запросы к `www.youtube.com` и `www.cloudflare.com`, сохраняет локальный текстовый отчёт и ничего не загружает автоматически. Конфиги ITG Ray, подписки, ключи, история браузера и командные строки процессов не собираются. Отчёт содержит IP-адреса, DNS, маршруты и названия адаптеров: перед пересылкой просмотри его, публично без проверки не выкладывай.

## Как собрать сравнение

Сохрани `.ps1` в отдельную папку. Открой в ней PowerShell, желательно от администратора, чтобы получить сведения о драйверах и брандмауэре. Без повышения прав недоступные разделы будут помечены `UNAVAILABLE/ERROR`, сбор продолжится.

Выполни три запуска по очереди. Метка `-Label` только подписывает отчёт: переключать VPN и IPv6 нужно вручную. Во всех запусках оставь тот же сервер VPN, сеть, правила маршрутизации и состояние zapret/GoodbyeDPI. Дождись строки `Saved:` перед следующим переключением.

1. Отключи VPN кнопкой в ITG Ray:

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\diagnose-windows-network.ps1 -Label off
   ```

2. Выбери режим TUN, IPv6 `disabled` и подключись:

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\diagnose-windows-network.ps1 -Label tun-disabled
   ```

3. Отключись, выбери предпочтение IPv4 (`prefer-v4`) и подключись заново:

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\diagnose-windows-network.ps1 -Label tun-prefer-v4
   ```

`ExecutionPolicy Bypass` применяется только к запущенному процессу PowerShell, системная политика не изменяется. При корпоративном запрете запуска скриптов согласуй запуск с администратором.

Один запуск обычно занимает 1–3 минуты. Отчёты появятся в папке `ITGRay-diagnostics` на рабочем столе; иной путь задаётся через `-OutputDirectory C:\Temp\ITGRay-diagnostics`. Если SOCKS-порт изменён в настройках клиента, добавь `-SocksPort 12345` с фактическим портом; по умолчанию проверяется `127.0.0.1:1080`. Можно добавить `-ClientVersion '0.1.2-beta.1'` с установленной версией.

Пришли три отчёта, версию клиента и небольшой фрагмент его лога со временем проверки и адресом назначения ошибки, убрав адрес VPN-сервера и секреты. Укажи браузер и работает ли в нём защищённый DNS. Не присылай полный конфиг или подписку.

## Как читать результат

В текущей реализации TUN при IPv6 `disabled` всё ещё захватывает IPv6. Для трафика, не совпавшего с более ранними правилами LAN/пользователя, добавляется `::/0 → block`; DNS использует `ipv4_only`. В sing-box 1.13.11 блокирующий outbound возвращает `syscall.EPERM` — `operation not permitted`. Поэтому такая строка с IPv6-адресом совместима со штатной блокировкой. Подтверждение для конкретного случая — соседняя строка `outbound/block` / `blocked connection` с тем же адресом или идентификатором соединения. Одна фраза ошибки не устанавливает причину.

| Наблюдение | Что проверять дальше |
| --- | --- |
| При `disabled` HTTPS IPv4 работает, IPv6 не работает | Это совместимо с выбранной политикой. Ошибка IPv6 сама по себе не доказывает поломку Windows и не объясняет зависание всего сайта. |
| В `off` IPv6 не работает на обоих сайтах | Проверить наличие IPv6 у провайдера, адрес, маршрут и DNS; отсутствие нативного IPv6 может быть нормальным. Это ещё не доказательство повреждения стека. |
| В `off` не работает только YouTube | Возможна блокировка у провайдера. Сравни с Cloudflare; не принимай это за неисправность IPv6 целиком. |
| OS-route IPv4 не работает в TUN, SOCKS работает | Сузить поиск до пути TUN, DNS, маршрутов и сетевых фильтров. SOCKS обходит часть локальной обработки, но продолжает использовать прокси и его правила. |
| SOCKS тоже не работает | Проверить наличие слушателя и правильность порта; затем соединение с сервером и логи ядра. Это не доказательство проблемы Windows. |
| При `prefer-v4` проблема исчезла | Различие связано с режимом обработки IPv6/DNS, но для исправления нужны адреса и логи неудачных соединений. |
| Везде HTTPS проходит, браузер всё ещё зависает | Проверить браузерный DoH, кеш, расширения и QUIC/UDP отдельно: скрипт проверяет TCP/HTTP 1.1, без воспроизведения видеопотока и запросов к `googlevideo.com`. |
| Найден WinDivert/zapret | Это только факт наличия процесса/драйвера, а не доказательство конфликта. Отсутствие совпадения по имени также не исключает сторонний фильтр. |

`HTTPS OS-route` игнорирует явный прокси, но при активном TUN всё равно идёт через маршрутизацию Windows и туннель. `HTTPS SOCKS remote DNS` передаёт имя прокси: этот тест не принуждает сервер использовать IPv6. DNS-пробы A/AAAA используют системный DNS без файла hosts; браузерный DoH они не воспроизводят. Пустой AAAA при `disabled` может быть ожидаемым; адреса FakeIP не означают ошибку DNS.

В HTTPS-разделах смотри `ExitCode`, `TimedOut`, `Stderr`, HTTP-код и времена соединения/TLS. `ExitCode=0` означает завершённую передачу curl, но HTTP 403/5xx не считается успешной загрузкой сайта. Ошибка сертификата не означает повреждение IPv6. Не сбрасывай Winsock и не отключай IPv6 во всей Windows по одному сообщению `operation not permitted`.

Основания: [правило блокировки в ITG Ray](../internal/configgen/singbox.go), [block outbound sing-box 1.13.11](https://github.com/SagerNet/sing-box/blob/v1.13.11/protocol/block/outbound.go).

## Проверка скрипта

```powershell
powershell.exe -NoProfile -File .\scripts\test-windows-network-diagnostics.ps1
```

Тест проверяет синтаксис, сохранение stdout/stderr и кода ошибки, ограничение времени процесса и продолжение отчёта после ошибки отдельного раздела. Windows CI также запускает сбор на тестовой машине; это не заменяет проверку на проблемной Windows 10 с активным TUN.
